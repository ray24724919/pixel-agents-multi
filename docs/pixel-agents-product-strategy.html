2026-06-01 · Productization Brief

把可愛的 agent 辦公室，升級成可信賴的 AI 工作控制台。

Pixel Agents Multi 現在已經跨過「Windows 可以正常安裝、可辨識自有 extension、能看到 Codex/Claude agents」這一關。下一步不應只是繼續堆功能， 而是把它產品化成一個讓人放心監督多個 AI 工作流的控制台。

目前身份：raychen.pixel-agents-multi 產品核心：多 agent 可視化與管理 建議主軸：Local-first Agent Operations

一句話結論

不要把 Pixel Agents Multi 做成「漂亮的監看玩具」。應該把它做成「本機優先、 隱私可信、能讓使用者同時管理多個 AI 工作者」的 VS Code agent cockpit。

這個產品最有價值的不是 pixel art 本身，而是它把原本散落在 terminals、 JSONL、SQLite、Claude/Codex 狀態裡的工作，轉成使用者能一眼理解、能介入、 能回顧、能做決策的操作介面。Pixel art 是親和力，Agent Center 才是長期價值。

產品定位

不是什麼

  • 不是單純的 Claude/Codex launcher。
  • 不是聊天記錄瀏覽器。
  • 不是 token billing 報表工具。
  • 不是通用 team management SaaS。

是什麼

  • 多 AI agent 的本機工作狀態控制台。
  • 跨 provider、跨 project、跨 thread 的即時可視化層。
  • 讓使用者知道「誰在工作、卡在哪、花了多少、下一步該做什麼」。

長期賣點

  • Local-first，不把 transcript/token 資料送到雲端。
  • 可同時理解 Codex、Claude Code、Claude Cowork。
  • 把 AI 工作流從黑箱終端變成可管理的系統。
建議定位句： Pixel Agents Multi is a local-first agent operations cockpit for developers who supervise multiple AI coding agents across providers and projects.

目標使用者與 Jobs To Be Done

使用者類型 當前痛點 Pixel Agents Multi 應該完成的工作 最重要的產品訊號
個人 power user 同時開多個 Codex/Claude 工作，常忘記誰在等、誰在跑、誰已經卡住。 一眼看懂所有 agent 的狀態，快速 focus/refresh/inspect/close。 agent count 正確、等待狀態清楚、refresh 不重複。
AI supervisor 型開發者 需要把工作切成多包派下去，但缺少總控台與任務歷史。 把 agent、project、task、timeline、usage 串成可追蹤的工作流。 Agent Center 的資訊密度、Timeline、task handoff quality。
小團隊 tech lead 想導入 AI agents，但不信任不可見的成本、狀態與副作用。 提供 local-first 可審計介面，讓 lead 看見工具使用、token 趨勢、風險。 Usage analytics、audit trail、privacy guarantee。
開源/擴充套件使用者 擔心 fork 和上游 extension 混淆，不知道裝的是哪一個。 清楚的 extension identity、版本、release checklist、安裝驗證。 publisher/name/VSIX/version/displayName 一致。

產品設計原則

可信優先

agent 數量、provider、project、token、狀態必須比視覺效果更可靠。可愛但不準， 使用者很快就會失去信任。

Local-first

預設資料都在本機，明確說明讀取哪些檔案。若未來有 cloud sync 或 telemetry， 必須 opt-in。

管理而非打擾

面板應該降低認知負擔。狀態異常才突出，正常運作時保持安靜、可掃描。

可復原

Refresh、hide、archive、kill、layout import 都要可預期。使用者不能害怕按按鈕。

確保每次 reload/refresh 都不丟 agent、不重複、不誤判 provider。這是地基。

高優先 UX information architecture

不只顯示 token，而是回答「哪個 project 最花、哪個 agent 最有效、成本趨勢是否異常」。

高優先 analytics budget

讓使用者能從「看 agent」進一步變成「管理工作包」：派工、暫停、接續、匯總報告。

Usage 與 token 資訊設計

Usage 不應塞在同一個小區塊裡硬撐。建議採用「總覽小卡 + 獨立分析頁」。 平常只看異常和總量；需要理解成本時，進入完整 Usage Analytics。

建議資訊架構

  • Canvas bottom strip：只顯示 provider totals 與異常提示。
  • Agent Center / Usage tab：顯示 provider、project、agent、thread 層級。
  • Detail drawer：點 agent 後看該 agent 的 token、tools、timeline、session path。
  • Export：CSV/JSON 匯出，方便長期分析。

可以借鏡 llm-usage-dashboard 的地方

  • 按時間聚合 token usage。
  • 按 model/provider/project 拆分。
  • 顯示趨勢而不只顯示累計。
  • 把估算和精確值分開標示。

Usage Analytics 應該回答的問題

花在哪裡？

依 provider、project、agent、thread 分解 token 與 proxy cost。

有沒有異常？

偵測 token 急升、cache 失效、某個 agent 重複消耗。

值不值得？

把 usage 和 outcome 串起來，例如完成工作包、產生 commit、修掉測試。

文字策略： 持續使用「API proxy estimate」這種說法，不要暗示它等於訂閱帳單。這可以避免誤導。

Agent Center 2.0 設計方向

你前面提到希望像 Google 書籤那種「點進另一頁」的感覺，這個直覺是對的。 目前 modal 容易擠，未來可以把 Agent Center 做成大分頁，而不是小視窗。

建議版型

  • Canvas 是第一頁：保持 pixel office 的情緒與即時狀態。
  • Agent Center 是第二頁：接近 GitHub issue/project table 的資訊密度。
  • Usage 是第三頁：完整 dashboard，不再塞在小 modal。
  • Settings/Layout 是工具頁：不要干擾日常監督。

視覺語氣

  • Canvas 可以保留 pixel 風格。
  • Agent Center 可以更像 GitHub/Linear：清楚、表格化、可掃描。
  • Usage 可以更像 analytics：圖表、時間軸、filter bar。
  • 整體仍保留少量 pixel accents，避免變成兩個產品。

功能設計草圖

區域 核心內容 互動 設計重點
Top bookmark tabs Office / Agents / Usage / Timeline / Settings 一鍵切換大頁面 讓使用者感覺是進到不同工作頁，不是打開彈窗。
Agents table provider、name、project、status、tokens、last event filter、sort、search、row detail 比卡片更適合大量 agent。
Agent detail drawer session path、timeline、actions、usage、terminal focus focus、pause/resume、archive、kill 危險操作集中，不污染主表。
Usage analytics provider/project/model/time trend date range、export、threshold 從數字變成決策工具。

建議路線圖

v1.3.x

Stabilization and release confidence

目標是把目前的 Windows 成果守住：安裝、刷新、Claude/Codex 顯示、Usage 不空白、 package identity 不混淆。

  • 加入 `npm run verify:release`，封裝 W3-I 那些檢查。
  • 加一個 VS Code command：`Pixel Agents Multi: Diagnostics`，輸出 identity、agents、paths。
  • 建立 stable/dev VSIX 命名規則。
v1.4

Agent Center 2.0

把現在的 modal 式 Agent Center 拆成更像書籤/頁面的資訊架構，讓大量 agent 也不會擠。

  • 大頁面 tabs：Office、Agents、Usage、Timeline。
  • Agents table + detail drawer。
  • Search/filter/sort。
  • 清楚處理 hidden/archived/killed agents。
v1.5

Usage Intelligence

把 token usage 從數字升級成洞察。這是最接近「每天會回來看」的產品面。

  • Provider/project/agent/thread 聚合。
  • 時間趨勢與異常偵測。
  • Budget threshold 與本機提醒。
  • CSV/JSON export。
v1.6

Supervisor workflow

把「看到 agent」推進到「管理 agent 工作」。這會讓 Pixel Agents Multi 更像真正工作台。

  • Task package templates。
  • Agent handoff report generator。
  • Pause/resume/bulk actions。
  • Project-level outcome timeline。
v2.0

Repo-centered collaboration

在正式 team platform 之前，先用 git repo 變成共享事實來源。這可以保留 local-first 的優點，同時讓多人看到工作成果與交接狀態。

  • Agent handoff reports 寫回 repo。
  • Branch/commit/PR 與 agent work state 關聯。
  • 可共享 artifact summary，而不是同步私人 transcript。
  • Project timeline 以 repo events 為核心。
v2.5+

Team / Lab Mode

等個人 local cockpit、usage intelligence、repo-centered collaboration 都穩定後， 再進入 3-5 人小團隊共用的 AI lab 平台。

  • Team space with opt-in shared agent status。
  • Project-level collaboration map。
  • Shared artifacts、handoff summaries、PR/issue links。
  • Visibility model：private / project / team。

Team / Lab Mode 長期方向

這是很有價值的產品層級，但我會把它放在後面：先把本地個人使用、監測、Usage Intelligence、Agent Center 都打穩，再做小團隊平台。否則 team mode 只會放大目前的 agent detection、refresh、資料模型問題。

Team mode 不應該是「監控每個人的 AI 聊天紀錄」，而應該是「讓小團隊看見可共享的工作狀態、 artifact、handoff 與 repo 進度」。

Personal Local Cockpit

每個人先有穩定的本機 Pixel Agents：agent 狀態、Usage、Timeline、Refresh、Kill/Archive 都可靠。

現在到 v1.6

Repo-centered Collaboration

不急著做 server。先把 git repo、branch、PR、issue、handoff markdown 當成共享語言。

v2.0

Team / Lab Platform

3-5 人登入一個 lab space，各自同步可共享 agent 狀態與成果，不預設同步私人 raw transcript。

v2.5+

Team / Lab Mode 可以呈現什麼

畫面 內容 價值 隱私預設
Team room 每個成員目前有幾個 agent、在哪些 project、狀態是 working/waiting/blocked/done。 讓 lead 或 lab 成員知道現在團隊 AI 工作分布。 只同步狀態與摘要，不同步完整 prompt。
Project collaboration map 同一 repo 裡有哪些 agent thread、branches、handoff reports、PRs。 避免多人或多 agent 在同一 project 裡互相踩線。 以 repo artifact 為主。
Handoff feed agent 完成的摘要、修改檔案、branch、commit、下一步建議。 讓其他人或其他 agent 能接續，而不是重讀整段聊天。 handoff summary 可編輯後分享。
Team usage intelligence 按 member/project/provider/model 聚合 usage 與趨勢。 讓小團隊知道哪裡消耗最多、哪種工作最有產出。 預設只看聚合，不看私人 transcript。

現在就該預留的資料模型

Local agent record

  • `agentId`、`provider`、`projectDir`、`repoRoot`
  • `branch`、`commit`、`threadId`、`sessionPath`
  • `taskTitle`、`status`、`lastEventAt`
  • `visibility: private | project | team`

Shared artifact record

  • `artifactType: report | patch | branch | pr | note`
  • `summary`、`owner`、`sourceAgentId`
  • `repoPath`、`branch`、`commitSha`、`prUrl`
  • `sharedAt`、`visibility`、`redactionStatus`
產品節奏建議： Team/Lab Mode 先做 research + architecture，不要現在開發。短期可以先要求 executor 產出資料模型、隱私模型、repo-centered handoff protocol，等個人版功能成熟後再落地。

發行策略建議

短期：Local VSIX first

現階段先不要急著 Marketplace。你的產品還在高速探索期，local VSIX 能保持迭代速度，也比較適合驗證真實工作流。

  • 每次 release 都產出 handoff report。
  • VSIX filename 固定：`pixel-agents-multi-<version>.vsix`。
  • 安裝後必查：`raychen.pixel-agents-multi@<version>`。

中期：Stable / Dev channels

當你開始頻繁試 UX，可以拆 stable 和 dev，避免自己的日常工具被實驗版弄壞。

  • Stable：只放通過 W3-I 類 release gate 的版本。
  • Dev：新 UI、新 usage graph、新 provider scanner。
  • 命名要避免混淆，例如 `Pixel Agents Multi Dev` 要有不同 extension id。

建議加入的 release guard

Guard 檢查內容 為什麼重要
`npm run verify:identity` package id、publisher、commands、view ids、settings、docs 一致。 避免和上游 extension 或舊版 fork 混淆。
`npm run verify:vsix` 跑 `vsce ls` 並確認 include/exclude 清單。 避免把 roadmap、tests、AGENTS.md 打包出去。
`npm run verify:installed` 安裝 VSIX 後檢查 `code --list-extensions`。 確保使用者真的裝到自己的 extension。
`npm run verify:live-smoke` 用 UI Automation 或 Playwright 驗證正常 VS Code 面板。 避免只在 Extension Development Host 通過。

風險與產品護欄

Provider 行為變動

Codex/Claude 的本機檔案格式、SQLite schema、hook events 都可能變。需要把 scanner 風險視為產品核心風險，而不是偶發 bug。

護欄： provider adapters、schema probe、diagnostic report。

Usage 誤導

token 與 proxy cost 很容易被誤解成真實帳單。這會傷害信任。

護欄： exact/estimated/proxy 三種標示永遠分清楚。

UI 擁擠

Canvas、Agent Center、Usage、Timeline 都塞一起會變成四不像。

護欄： 大頁面 tabs，Canvas 和 analytics 分工。

自有發行混淆

如果 publisher/name/view ids 或 user data path 漏掉一處，就可能和上游公開版互相污染。

護欄： release identity guard 自動化。

最終建議

Pixel Agents Multi 的下一步不是「做更多裝飾」，而是建立一個可信任的操作層： 讓使用者能監督多個 agent，能知道成本與狀態，能安全地 refresh、archive、kill， 也能把結果交接成 report。只要這條線走穩，pixel art 會成為它的個性，而不是它唯一的價值。
